## 1. 배포 범위 결정

필수 1차 배포는 기존 절세 가이드의 본문 정정·체크리스트·사례·기존 계산기 연결이다. 카드·연금 시나리오는 이미 구현돼 있으므로 엔진을 재작성하지 않는다. [사이트 검토](07_실제_사이트_대조_검토_및_구현_확정안.md)의 R-01/R-02와 본문 정정 목록을 선행 기준으로 한다.

| 기능 ID | 기능 | 1차 배포 |
|---|---|---|
| TAX-R01 | 기존 본문 정정·재편과 귀속·정산연도 구분 | 필수 |
| TAX-R02 | 6개 공제 항목 체크리스트 | 필수 |
| TAX-R03 | 계산기 CTA·준비자료 안내 | 필수 |
| TAX-R04 | 공제·결정세액·환급 사례 | 필수 |
| TAX-R05 | 체크리스트 로컬 저장 | 이번 구현 제외 |
| TAX-C01 | 기존 카드 시나리오 연결·회귀 확인 | 기존 기능 유지 |
| TAX-C02 | 기존 연금계좌 효과 연결·회귀 확인 | 기존 기능 유지 |

유지 경로는 `/reports/2026-year-end-tax-saving-guide/`, 연결 계산기는 `/tools/year-end-tax-refund-calculator/`다. 새 체크리스트 URL·새 redirect·등록 중복을 만들지 않는다.

실제 변경 파일: `src/pages/reports/2026-year-end-tax-saving-guide.astro`, `src/data/yearEndTaxSavingGuide2026.ts`, `src/styles/scss/pages/_2026-year-end-tax-saving-guide.scss`. 새 인터랙션은 `public/scripts/2026-year-end-tax-saving-guide.js`로 분리한다. `src/data/reports.ts`, 홈·리포트 허브·sitemap은 기존 항목을 유지하며 바뀐 메타만 반영한다. 기존 계산기 데이터·페이지는 관련 링크 조정이 필요할 때만 최소 변경한다.

구성: BaseLayout + SiteHeader + CalculatorHero + InfoNotice + 기존 yets-page 섹션 + SeoContent. SiteFooter는 BaseLayout이 이미 렌더링하므로 중복 추가하지 않는다. 새 차트는 필요 없으며, 정정·삭제하는 환급 차트에만 쓰인 Chart.js 코드·의존 로드도 정리한다. 본문·FAQ·사례·출처는 TS 데이터로 모으고 안전하게 JSON을 주입한다.

체크 상태가 세션 재생에 자동 수집되지 않도록 이 리포트는 기존 BaseLayout의 `recordSessions={false}` 옵션을 사용한다. 체크 상태를 분석 payload로 보내는 이벤트는 만들지 않는다. 계산기에 이동할 때는 기존 계산기의 `recordSessions={false}`, `loadAds={false}`, no-referrer 설정을 보존한다. 공유 fragment 정책은 이번 작업으로 바꾸지 않는다.

## 3. 콘텐츠 데이터 모델

```ts
type ChecklistItemId = 'card' | 'retirement' | 'rent' |
  'medical' | 'dependents' | 'donation';
type Applicability = 'unknown' | 'applies' | 'not_applicable';
type Preparation = 'unchecked' | 'in_progress' | 'ready';
type ChecklistItem = {
  id: ChecklistItemId;
  title: string;
  checkNow: string[];
  actByYearEnd: string[];
  documents: string[];
  conditions: string[];
  sourceIds: string[];
  relatedAnchor: string;
};
type ChecklistState = Record<ChecklistItemId, {
  applicability: Applicability;
  preparation: Preparation;
}>;
type TaxReport = {
  id: '2026-year-end-tax-saving-guide';
  taxYear: 2026;
  settlementYear: 2027;

```

실제 본문 형식은 기존 CMS·Markdown·콘텐츠 모델을 유지한다. `unknown`은 임의 HTML 삽입을 허용한다는 뜻이 아니라 저장소에서 쓰는 안전한 콘텐츠 타입으로 바꿀 자리다. URL·본문 HTML은 기존 검증·이스케이프 정책을 적용한다.

## 4. 체크리스트 상태와 집계

기획서의 ‘모두 해당 없음’을 구현하기 위해 해당 여부와 준비 상태를 분리한다. 준비 완료는 공제 적격 판정이 아니라 자료 준비 상태다.

초기: 모든 항목 `unknown + unchecked`.

- 적용함 선택: preparation을 유지하고 해당 항목으로 집계.
- 비해당 선택: preparation을 unchecked로 리셋, 완료율 분모에서 제외.
- 다시 미확인 선택: preparation을 unchecked로 리셋.
- 준비 상태 변경: applies일 때만 가능.
- 초기화: 현재 메모리의 모든 체크 상태를 초기값으로 복구.

집계 계약:

```text
applicableCount = applies 항목 수
readyCount = applies 이면서 ready인 항목 수
unknownCount = unknown 항목 수
```

모든 항목 비해당이면 ‘해당한다고 선택한 항목이 없습니다’라고 표시한다. 분모가 0인 100%를 표시하지 않는다. 미확인 항목이 남아 있는데 전체 점검 완료로 표시하지 않는다.

## 5. 무저장·기한 전환

준비 상태는 페이지 메모리에만 보관한다. localStorage·URL·서버·분석에 상태를 저장하지 않는다. 새로고침하면 초기 상태다. 저장 기능과 자동 복원·만료 처리는 후속으로 분리하며 이번 범위에는 관련 코드·체크박스를 넣지 않는다.

연말 이후에는 `contentPhase = preparation | settlement | archive` 설정으로 행동 문구를 바꾼다. 날짜 자동 전환만으로 미검토 본문을 공개하지 않고 편집 설정과 수정 이력을 함께 반영한다. 2027년 1월에 이미 지난 납입 행동을 ‘지금 할 일’로 남기지 않는다.

## 6. 기존 계산기 연결 계약

기본 CTA는 canonical 경로만 전달한다. 페이지 간 급여·납입액을 query나 hash로 넘기지 않는다. `#retirement`처럼 비민감 섹션 앵커는 기존 계산기에 해당 ID가 실제 존재할 때만 사용한다.

CTA placement는 hero / retirement_section / footer로 고정한다. 클릭 분석에 이 placement와 목적지만 열거값으로 전달한다. 현재 referrer를 통째로 재전송하지 않는다.

계산기 진입 준비물: 예상 총급여, 공제대상 지출, 적격 연금계좌 납입액, 기납부세액. 기납부세액 미입력 추정 기능이 있으면 결과에 추정 배지를 표시하고 실제 입력과 구분한다.

## 7. 카드 시나리오 확장 계약

아래 타입과 함수명은 기존 기능을 설명하는 개념 계약이다. 현재 구현은 `public/scripts/year-end-tax-refund-calculator.js`의 `createCalculator` 안에 `calcCardDeduction`, `calcPensionCredit`, `compareScenario`를 갖는다. 이 단계에서 아래 타입대로 별도 엔진을 만들지 않는다. 기존 엔진이 국세만 계산하고 기납부 미입력 시 환급 null을 반환하는 실제 범위를 유지한다.

```ts
type SpendCell = {
  method: 'credit' | 'debit' | 'cash_receipt';
  category: 'general' | 'market' | 'transit' | 'culture_sports';
  amountWon: bigint;
};
type CardScenarioInput = {
  taxYear: 2026;
  grossAnnualSalary: bigint;
  current: SpendCell[];
  plannedEligibleSpend: SpendCell[];
  context: VerifiedCardEligibility;
};
type CardDeductionBreakdown = {
  eligibleSpend: bigint;
  threshold: bigint;
  baseDeduction: bigint;
  additionalDeduction: bigint;
  totalDeduction: bigint;
  appliedCapIds: string[];
};
type CardComparison = {
  before: CardDeductionBreakdown;
  after: CardDeductionBreakdown;
  deductionDelta: bigint;
  estimatedTaxDelta: bigint | null;
};
```

지출은 결제수단×사용처의 교차 셀로 저장한다. 각 지출이 일반/특별 사용처에 중복 포함되지 않도록 한다. 집계 금액을 입력할 때 ‘일반 사용액은 특별 사용처를 제외한 금액’이라고 설명한다. 배포에 필요한 분류·특례가 이 타입에 추가로 있다면 공식 규칙 검토 후 셀과 eligibility를 확장한다.

`VerifiedCardEligibility`는 2026 카드 공제 규칙에서 실제 필요한 요건을 수집한 타입이다. 총급여 외 조건이 검증되지 않은 상태에서 가족수 등 필드를 추정해 고정하지 않는다. 해당 타입과 공제 한도 표가 미완성인 경우 기능은 끈다.

함수:

```ts
calculateCardDeduction(input, rules): CalcResponse<CardDeductionBreakdown>
compareCardScenarios(input, rules, optionalFullTaxContext): CalcResponse<CardComparison>
```

동일 예정 지출을 결제수단별로 비교할 때 기준 총 지출은 같아야 한다. 먼저 before를 완전 계산하고 current+planned를 같은 연도 함수로 다시 계산한다. 문턱 차감 순서와 한도는 데이터화된 법정 규칙을 따른다. 한계세율 입력만으로 확정 환급액을 반환하지 않는다.

전체 세액 엔진과 필요한 입력이 검증되면 두 시나리오의 결정세액 차이를 계산한다. 없으면 estimatedTaxDelta=null로 두고 소득공제 차이만 표시한다. ‘모르는 값’을 0원 절세로 바꾸지 않는다.

## 8. 연금계좌와 환급 결과 계약

일반 연금계좌는 본인 납입 연금저축과 공제 적격 퇴직연금 납입액을 분리한다. 사용자 부담금·퇴직금 이전·ISA 특례 등은 일반 수식에 섞지 않는다. 특례 선택 시 지원하지 않는다면 안내하고 계산을 제한한다.

출력 타입은 최소한 다음을 구분한다.

```ts
type RetirementEffect = {
  eligibleContributionBefore: bigint;
  eligibleContributionAfter: bigint;
  statutoryCreditDelta: bigint;
  actualLiabilityReduction: bigint | null;
};
type Settlement = {
  determinedIncomeTax: bigint;
  prepaidIncomeTax: bigint | null;
  prepaidKind: 'actual' | 'estimated' | 'unknown';
  settlementDelta: bigint | null; // 선납 - 결정세액, 양수 환급
};
```

국세·지방세를 포함하는 결과라면 각각 분리 필드를 추가하고 같은 범위끼리 차감한다. 국세 기납부액에서 국세+지방세 결정액을 빼지 않는다. 환급이 음수인 경우 ‘추가 납부 예상’과 절대값으로 표현한다.

기획서 교육 예시의 문턱·한도·납입한도는 [기획서 공식 근거](../../plan/202611/01_연말정산_2026_귀속_리포트_기획.md)의 2026 적용 검토 후 rules에 입력한다. 설계 코드에 확정 상수로 중복 작성하지 않는다.

## 9. 편집·SEO 구현

H1 1개, 고정 H2 anchor, Article 및 breadcrumb는 기존 사이트 방식 재사용. FAQ 답변과 출처를 초기 HTML에 포함한다. 체크리스트 상태는 검색용 콘텐츠를 바꾸지 않는다.

콘텐츠 예시는 모두 가정을 함께 보관한다. `TaxExample`은 id, title, assumptions, inputs, expectedExplanation, sourceIds로 구성한다. 계산 엔진 사례가 아닌 개념 사례는 `exampleKind='educational'`을 명시해 자동 결과처럼 렌더링하지 않는다.
