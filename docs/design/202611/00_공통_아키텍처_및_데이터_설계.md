## 3. 논리 구조

```text
검토한 공식 자료 ─→ 출처 장부 ─→ 규칙·실적 데이터 ─→ 빌드 검증
                                                    │
                               ┌────────────────────┴─────────────┐
                               ↓                                  ↓
                      검색 가능한 본문·표                 브라우저 계산 규칙 번들
                                                                  │
사용자 입력 → 원문 문자열 → 검증·정규화 → 순수 계산 → 결과 ViewModel → 화면
                                                    │
                                                    └→ 허용 목록 기반 이벤트
                                                       (금액·입력값 제외)
```

출처를 브라우저에서 실시간 수집해 계산하지 않는다. 편집 담당이 수집하고 검토한 데이터만 배포 번들에 포함한다. 네트워크가 끊겨도 로드된 계산기에서는 계산이 가능해야 한다. 외부 분석 도구 실패는 계산·본문 표시를 막지 않는다.

```text
data/rules/tax/                  카드·연금계좌·해외주식
data/earnings/                   기업 분기 원시 수치·방법론
domain/money/                   정수 금액·유리수·단수 처리
domain/rules/                   기간 선택·검증 상태·기능 가용성
domain/calculators/             독립적인 계산 함수
presentation/                   화면 상태·문구·ViewModel 변환
components/                     기존 UI에 매핑하는 컴포넌트
verification/fixtures/          수기·공식 예시와 기대값
```

위 경로는 논리 책임 설명이다. 실제 구현은 `src/data/<feature>.ts`, `src/pages/{tools,reports}/<slug>.astro`, `public/scripts/<slug>.js`, `src/styles/scss/pages/_<slug>.scss`에 매핑한다. 공통 브라우저 계산 모듈이 필요한 경우 기존 public/scripts의 ES module 패턴을 사용한다. domain/presentation 디렉터리 묶음을 일괄 신설하지 않는다.

핵심 경계는 계산 함수가 DOM·스토리지·HTTP·분석 이벤트에 의존하지 않고, 데이터가 원고 곳곳의 수동 상수로 흩어지지 않는 것이다. 기존 number 기반 엔진 전체를 이번 작업에서 bigint로 바꾸지 않는다. 정밀 계산 원칙은 새 엔진에 적용하고 기존 호환은 독립적으로 검증한다.

## 5. 금액·비율·날짜 공통 계약

```ts
type IntegerString = string; // 정규식으로 검증한 10진 정수
type LocalDate = string;     // YYYY-MM-DD, 실재 날짜 검증
type YearMonth = string;     // YYYY-MM, 실재 월 검증
type Won = bigint;           // 런타임 계산 전용
type Ratio = { numerator: bigint; denominator: bigint };
type Unit = 'KRW' | 'USD';
type Rounding = {
  increment: IntegerString;  // 1원, 10원 등 검증된 단위
  mode: 'floor' | 'truncate' | 'half_up' | 'ceil';
};
```

영구 데이터·JSON에는 bigint를 직접 쓰지 않고 정수 문자열을 쓴다. 비율도 문자열 분자·분모로 직렬화한다. 예를 들어 4.75%는 475/10000이다. 음수가 가능한 실적·손익과 음수가 불가능한 급여·손실 절대값을 타입 검증 단계에서 나눈다.

금액 입력 처리: 양끝 공백 제거 → 허용한 원 단위 숫자/정상 천 단위 쉼표 검사 → 쉼표 제거 → 10진 정수 파싱 → 필드별 범위 검증. `1e6`, `3.5`, `12abc`, 비정상 쉼표는 오류다. ‘만원’ 자유 입력은 초기 미지원이며 화면에 원 단위를 항상 표시한다.

제품 입력 상한은 일반 계산기 필드당 1조원으로 제안한다. 이는 세법상 한도가 아니라 오입력·레이아웃 방지용 정책이다. 기업 재무 데이터에는 적용하지 않는다. 상한 변경은 UI·스키마·검증 예시를 함께 변경한다.

비율 계산은 `amount × numerator / denominator`를 정확한 유리수로 유지한 뒤 규정에서 정한 단계에만 단수 처리한다. 단계별 단수 규칙이 미검증이면 그 규칙을 확정 계산용으로 승격하지 않는다. 음수에서 floor와 truncate의 차이를 명시하고 공통 함수가 임의 대체하지 않도록 한다.

기간은 `[effectiveFrom, effectiveToExclusive)`로 통일한다. 날짜는 로컬 날짜로 비교하며 서버 시간대를 사용해 하루씩 밀리지 않게 한다. 단순 날짜를 자정 UTC 타임스탬프로 변환하지 않는다. 독자에게 보이는 현재일·마감은 Asia/Seoul 기준이다.

## 6. 출처·규칙 모델

```ts
type Evidence = {
  id: string;
  publisher: string;
  title: string;
  url: string;
  publishedAt: LocalDate | null;
  checkedAt: LocalDate;
  locator: string; // 조문, 표, 페이지 또는 본문 항목
  notes: string[];
};
type LegalStatus = 'effective' | 'enacted_future' | 'announced' | 'proposal';
type ReviewStatus = 'draft' | 'source_checked' | 'cross_checked';
type RuleMeta = {
  id: string;
  version: string;
  legalStatus: LegalStatus;
  reviewStatus: ReviewStatus;
  effectiveFrom: LocalDate;
  effectiveToExclusive: LocalDate | null;
  sourceIds: string[];
  calculationKind: 'official_estimate' | 'rate_only' | 'scenario';
};
```

법적 상태와 내부 검토 상태를 분리한다. 이미 공포됐지만 미래 시행인 규칙은 미래 적용월에서 사용할 수 있다. 반대로 기관 발표를 확인했다는 사실만으로 시행 규칙이 확정됐다고 간주하지 않는다.

계산 의존 규칙마다 `cross_checked` 및 허용된 법적 상태를 확인한다. 단순 요율 비교는 요율만, 고지액 추정은 요율·상하한·산정·절사·부담 배분 모두를 요구한다. 가정 모드는 사용자가 명시적으로 선택한 별도 규칙 묶음만 사용한다.

규칙 검색 결과는 0개면 `RULE_NOT_AVAILABLE`, 2개 이상이면 `RULE_PERIOD_CONFLICT`다. 최신 버전을 정렬해 아무거나 고르는 방식은 금지한다. 과거 정정은 manifest가 참조하는 버전을 명시적으로 교체하고 이전 버전은 이력으로 보존한다.

## 7. 계산 결과 계약과 가용성

```ts
type Issue = {
  code: string;
  field?: string;
  messageKey: string;
};
type Provenance = {
  ruleRefs: { id: string; version: string }[];
  sourceIds: string[];
  assumptions: string[];
};
type CalcResponse<T> =
  | { kind: 'ok'; value: T; provenance: Provenance; warnings: Issue[] }
  | { kind: 'unsupported'; issues: Issue[] }
  | { kind: 'unavailable'; issues: Issue[] }
  | { kind: 'invalid'; issues: Issue[] };
```

`ok` 안에서도 이론 요율 비교·기간별 추정·가정 시나리오는 값의 `basisKind`로 구분한다. 계산된 0원은 `ok`의 값이다. 미지원·자료 없음·오류를 0원으로 표시하지 않는다.

4대보험은 항목별 CalcResponse를 모아 합계 가용성을 판단한다. 미확정 고용보험을 뺀 소계는 `verifiedSubtotal`이고 전체 합계는 null이다. 0과 null의 차이를 ViewModel에서 유지한다.

## 8. 화면 상태와 사용자 동작

```ts
type FormState<TInput, TResult> = {
  phase: 'idle' | 'editing' | 'invalid' | 'ready' |
         'success' | 'unsupported' | 'unavailable' | 'internal_error';
  raw: Record<string, string | boolean>;
  normalized: TInput | null;
  result: TResult | null;
  inputRevision: number;
  resultRevision: number | null;
};
```

신규 계산기는 버튼 제출·즉시 계산 중 현재 쉘과 입력 수에 맞는 방식을 선택하되 입력 변경 후 오래된 결과를 남기지 않는다. 기존 환급 계산기는 실시간 계산을 유지하며 이번 STEP01에서 제출 방식으로 바꾸지 않는다. revision 모델은 필요한 비교 기능에만 적용하고 모든 기존 화면에 상태 프레임워크를 강제하지 않는다.

화면 동작 표:

| 동작 | 상태 변화 | 표시 |
|---|---|---|
| 처음 진입 | idle | 빈 입력, 결과 안내 |
| 값 입력 | editing/ready | 라벨·단위·도움말 |
| 잘못된 제출 | invalid | 첫 오류로 포커스, 필드별 메시지 |
| 정상 제출 | success | 결과 요약·상세 근거 |
| 미지원 조건 | unsupported | 이유·공식 확인 경로 |
| 검증 데이터 부족 | unavailable | 필요한 기준과 현재 가용 기능 |
| 초기화 | idle | 금액·결과·시나리오 삭제 |
| 내부 계산 예외 | internal_error | 재입력 안내, 민감값 없는 오류 코드 |

오류 문구는 “오류가 발생했습니다” 대신 “비과세 급여는 세전 월 급여보다 클 수 없습니다”처럼 수정 행동을 알려준다. 긴 계산이 아니라면 로딩 스피너를 인위적으로 넣지 않는다.

## 10. 접근성·SEO·저장소

라벨/오류 설명을 입력과 연결하고 결과는 제출 후 `aria-live` 영역에서 핵심 한두 문장만 알린다. 결과 전체를 매 키 입력마다 읽지 않는다. 탭·라디오·details 등은 기존 접근성 있는 기본 패턴을 따른다. 표에는 caption과 헤더 연결을 둔다. 차트에는 동일 값의 표와 짧은 텍스트 설명을 제공한다.

본문·FAQ·출처·대표 예시는 초기 HTML에 포함한다. 개인 결과는 초기 HTML에 임의 생성하지 않는다. canonical은 기본 경로 하나로 통일한다. 신규 경로의 실제 충돌과 기존 구조화 데이터는 저장소 확보 후 확인한다.

입력값을 query/hash·서버 세션·분석 payload에 넣지 않는다. 링크 복사는 canonical만 복사한다. 초기 계산기 저장은 없음이다. 리포트 체크리스트 저장은 별도 명시 선택 기능이며 완료 상태도 세금 판단 결과가 아님을 설명한다.

## 11. 이벤트 계약

허용 payload: pageId, eventName, feature, mode, rulesetVersion, outcome, placement. 금액·가족 수·종목·자유 텍스트·raw 객체·result 객체는 금지한다. 허용 필드만 새 객체에 복사하는 방식으로 전송한다.

`calculator_complete`는 입력 검증과 계산이 성공한 제출에만 기록한다. unsupported/unavailable은 `calculator_outcome`의 열거값으로 구분한다. 서버 오류 로그에는 내부 코드·규칙 식별자만 남기고 사용자 입력을 붙이지 않는다. 페이지 재생·폼 자동 수집 기능은 이 페이지들에서 제외하도록 현재 분석 설정을 확인한다.

## 12. 배포와 변경 관리

배포 단위는 화면 코드·본문·규칙 manifest·대표 예시의 일치한 묶음이다. 코드만 새 버전, 규칙은 구버전인 상태를 막는다. 가용하지 않은 기능은 설정으로 숨기고 본문 CTA도 함께 바꾼다.

제안 manifest 필드: releaseId, contentVersion, enabledFeatures, pinnedRuleVersions, datasetVersion, sourceReviewDate. 계산 결과의 provenance는 manifest가 참조한 버전에서만 만든다.

롤백은 직전 검증된 묶음으로 되돌린다. 새 시행일 이후 과거 요율로 되돌려 잘못 계산할 가능성이 있으면 그 계산을 중단하고 안내·본문만 유지한다. 단순히 ‘이전 배포가 정상 작동했다’는 이유로 만료 규칙을 다시 쓰지 않는다.

## 13. 미해결 항목 관리

저장소·디자인·기존 모듈 매핑은 사이트 대조 문서에 반영했다. 공식 단수 처리·상하한, 최신 세액표, 기업 최종 데이터는 기능별 검토를 계속한다. 항목별 필요한 자료, 영향 기능, 대체 공개 범위를 [검증 명세](06_구현_작업_및_검증_명세.md)에 연결한다. 기존 환급 계산기의 입력 포함 fragment 공유와 새 기능의 기본 무저장 정책은 별도 상태로 기록한다.
