# 구현 작업·검증·배포 명세

버전: 2.0 | 작성일: 2026-11-10 | 사이트 대조 반영<br>
범위: 설계한 5개 콘텐츠의 구현 인계와 완료 판단<br>
주의: 아래 테스트는 수행해야 할 명세다. 실제 사이트 소스 구현·테스트·배포가 완료됐다는 기록이 아니다.

사이트 조사와 일부 기존 검증 스크립트 실행은 완료했다. [실제 검토 결과](07_실제_사이트_대조_검토_및_구현_확정안.md)를 따른다. STEP01은 기존 절세 가이드 개편, STEP05는 기존 연결실적 스냅샷 확장으로 수정한다. 신규 구조를 통째로 만드는 공통 작업보다 기존 파일·함수의 최소 확장을 우선한다.

## 1. 전체 작업 흐름

```text
저장소 확인
  → 기존 페이지·함수·분석 설정 조사
  → 공통 계약 매핑
  → 1번 리포트·기존 계산기 연결
  → 2번 국민연금 요율 비교·공용 monthly 모듈
  → 3번 해외주식 일반 계산·시나리오
  → 4번 보험별 모듈·불완전 합계·세금 분리
  → 5번 기업 데이터·표·차트
  → 페이지별 검수·배포·사후 점검
```

공개 콘텐츠는 기획서의 편성 순서를 유지한다. 내부 구현 의존성은 작업 티켓에 명시한다. 각 페이지는 독립 출시 가능하지만, 공용 모듈 변경이 먼저 출시한 페이지에 영향을 주면 해당 페이지의 관련 회귀 사례도 확인한다.

## 4. 필수 검증 분류

| 분류 | 목적 | 검증 대상 |
|---|---|---|
| 입력 검증 | 오입력으로 잘못된 결과 방지 | 빈칸/0, 음수, 쉼표, 소수, 큰 수 |
| 규칙 조회 | 다른 연도·기간 사용 방지 | 시행 전후, 상하한 경계월, 기간 중복 |
| 계산 golden case | 공식·독립 수기 기대값 대조 | 각 페이지 수치 사례 |
| 불변 조건 | 집계·모드 전환 오류 발견 | 합계 보존, 행 순서, 본인+회사 |
| 상태 전이 | 이전 입력 결과 혼동 방지 | 수정·전환·초기화·가정 해제 |
| 콘텐츠 일치 | 숫자·범위·설명의 정합성 | 본문·표·차트·메타·FAQ |
| 접근성 | 결과를 조작·이해 가능하게 | 키보드·라벨·오류·알림·대체 표 |
| 개인정보 | 민감값 비전송 | network·분석·오류·주소·저장소 |
| 배포 회귀 | 기존 기능·주소 보존 | 2026 계산·기존 URL·내부 링크 |

원고 문장만 바꾼 경우에는 과도한 계산 테스트를 추가하지 않는다. 계산 규칙·공용 함수가 바뀌면 영향을 받는 기능의 독립 예시와 경계를 실행한다. 정확히 무엇을 바꿨는지에 맞춰 검증 범위를 선택한다.

## 5. 핵심 불변 조건

1. rate_only 국민연금은 B가 고정이고 직장 본인+회사=전체가 유리수 기준으로 성립한다.
2. 공식 월 국민연금은 공식 단수·배분 규칙의 합계 관계를 만족한다.
3. 해외주식 계좌 행 순서·합계 모드 전환은 경제적 합계가 같으면 결과가 같다.
4. 같은 이익·비용 조건에서 손실만 늘리면 일반 모드 세금이 증가하지 않는다.
5. 해외주식 기본공제는 계좌 수에 따라 늘지 않는다.
6. 4대보험의 회사 표시 토글은 근로자 공제액을 바꾸지 않는다.
7. 4대보험 소계 비교는 전후 같은 항목 집합을 사용한다.
8. 비과세 현금 급여를 실수령액에서 이중 차감하지 않는다.
9. 기업 이익률의 분자·분모는 같은 레코드·통화·범위·기준이다.
10. 모든 결과의 규칙·데이터 버전은 현재 release manifest에 포함된다.

불변 조건은 독립 사례를 보완한다. 잘못된 규칙도 불변 조건을 만족할 수 있으므로 이것만으로 법정 계산 정확성을 판정하지 않는다.

## 7. 대표 fixture 형식

```json
{
  "id": "fixture-example",
  "feature": "pension_rate_only",
  "status": "draft",
  "ruleRefs": [],
  "inputs": {},
  "expected": {},
  "assumptions": [],
  "sourceIds": [],
  "independentlyReviewedAt": null
}
```

이 객체는 구조 예시이며 기대값이 없는 실제 테스트 fixture가 아니다. 출시 fixture는 입력·기대값·규칙 버전·근거가 모두 있어야 한다. 같은 함수를 실행해 나온 값을 그대로 기대값으로 저장하지 않는다. 교육용 예시와 공식 추정 fixture는 종류를 구분한다.

## 8. 배포 manifest 예시

```json
{
  "releaseId": "november-2026-design-example",
  "status": "draft",
  "contentVersion": "1.0",
  "enabledFeatures": [],
  "pinnedRuleVersions": [],
  "datasetVersion": null,
  "sourceReviewDate": null
}
```

샘플 manifest는 공개 계산 기능을 켜지 않는 상태다. 실제 배포에서는 기능별 필수 규칙과 검토 상태를 확인해 활성화한다. 모든 규칙이 아직 없는 것을 사이트 전체 실패로 처리하지 않고 해당 기능의 활성화를 막는다. 활성화된 기능의 필수 규칙이 없는 경우에는 배포 검증 실패다.

- [ ] 모든 금액 계산의 적용연도·기간·단위·검증 근거가 있다.
- [ ] 활성 기능에 연결된 draft 규칙·미검토 실적 레코드가 없다.
- [ ] 대표 기대값과 단수·기간 경계가 맞는다.
- [ ] 입력 변경 후 이전 결과가 현재 결과로 남지 않는다.
- [ ] 오류·미지원·미확정·0원을 구분한다.
- [ ] 개인정보가 query·hash·이벤트·오류·자동 폼 수집으로 전송되지 않는다.
- [ ] 저장 기능은 명시 선택·삭제·오류 처리를 지원한다.
- [ ] 본문·표·차트·메타가 같은 데이터·기준을 사용한다.
- [ ] 모바일 360px·일반 데스크톱·키보드로 핵심 기능을 쓸 수 있다.
- [ ] 기존 URL·canonical·사이트맵·상호 링크가 정상이다.
- [ ] 배포 후 대표 시나리오와 실제 전송 이벤트를 확인했다.

## 11. 사후 점검·오류 대응

배포 직후 실제 URL에서 계산·초기화·CTA·출처를 확인한다. 7일은 기능 오류·입력 이탈·계산 완료·미지원 outcome을, 28일은 검색어·유입·관련 콘텐츠 이동을 검토한다. 수익·검색 성과가 낮다는 이유로 검증되지 않은 제목이나 과장 수치를 추가하지 않는다.

잘못된 계산 발견 시: 영향 기능 식별 → 해당 규칙의 공개 사용 중단 또는 기능 비활성 → 공식 근거와 독립 재계산 → 수정·fixture 추가 → 결과 영향이 있는 수정 이력 → 배포·재확인. 개인정보 없는 계산 설계이므로 사용자의 과거 금액을 서버에서 찾아 재계산하는 절차는 만들지 않는다.

## 12. 인계 시 설명할 사항

이 문서 묶음은 실제 Astro+Vanilla JS 구조에 매핑한 설계이며 아직 사이트 코드를 변경한 결과는 아니다. TypeScript 블록은 핵심 계약 예시이고 기존 타입·함수에 매핑해야 한다. 새 라이브러리·DB·서버·대규모 계층을 도입해야 한다는 요구가 아니다.

구현 담당은 문서에서 임의로 빈 숫자를 채우지 말고 공식 자료와 적용 요건을 대조한다. 실제 저장소 구조로 매핑한 파일 목록, 선택한 구현 범위, 테스트 결과, 남은 검증 항목을 배포 기록에 남긴다.
