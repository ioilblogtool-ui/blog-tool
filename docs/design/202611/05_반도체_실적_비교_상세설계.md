## 1. 설계 결정

기존 삼성·마이크론 리포트에 SK하이닉스를 추가하고, 원시 실적 데이터에서 표·차트·요약 수치를 생성한다. 동일 숫자를 원고·표·차트에 수동으로 세 번 작성하지 않는다.

실제 구현은 `src/data/samsungMicronEarnings2026.ts`, `src/utils/samsungMicronEarnings2026.ts`, 대응 Astro·SCSS를 확장한다. `QuarterRecord`·`Snapshot`·`Source`·`ReportData`와 `validateReportData`·`buildReportView`·`buildJsonLd`가 이미 있으므로 아래 추상 타입을 새 데이터셋 엔진으로 그대로 복제하지 않는다. 단위·기간·출처·가용성 요구를 기존 타입에 매핑한다.

중요 변경: 메인 snapshot recordIds는 3사 연결실적, 삼성 DS는 segmentRecordIds다. 검증 함수를 느슨하게 해 DS를 메인에 섞지 않는다. 별도 공개가 필요한 필드만 기존 모델에 추가한다. 기존 `scripts/check-samsung-micron-earnings.mjs`를 확장해 과거 2사 스냅샷과 새 3사 스냅샷을 함께 확인한다.

1차 배포는 원통화 표·이익률 차트·기간/범위 설명·회사별 해설이다. 환율 환산·제품 구성·설비투자 비교는 같은 기준의 데이터가 확보될 때 추가한다. 공시 분기가 다른 사실을 숨기기 위해 분기명을 통일하지 않는다.

기획 단계에서 삼성·SK하이닉스 2026 Q3, 마이크론 FY2026 Q4 자료를 확인했다. 실제 공시 기간과 최종 값은 release dataset에 고정하고, 접속할 때마다 ‘latest’를 조회해 자동 교체하지 않는다.

## 2. 렌더링 구조

```text
 ├ ThreeCompanyPeriodCards

```

본문·핵심 표·출처는 초기 HTML에 포함한다. 차트도 가능한 범위에서 초기 렌더링하고, 브라우저 스크립트가 없어도 표로 같은 정보를 읽을 수 있게 한다. 일반 독자에게 데이터 검증 내부 코드를 노출하지 않고 비교 조건을 설명한다.

## 3. 원시 재무 데이터 타입

```ts
type CompanyId = 'samsung' | 'sk_hynix' | 'micron';
type ScopeId = 'consolidated' | 'semiconductor_ds' | 'memory_only';
type Framework = 'K_IFRS' | 'US_GAAP';
type Adjustment = 'reported' | 'non_gaap';
type MetricName = 'revenue' | 'operating_income' | 'net_income' | 'capex';
type DecimalString = string; // 부호·정수·선택 소수부, 지수 표기 금지
type MetricValue =
  | { status: 'available'; amount: DecimalString; scale: IntegerString;
      currency: 'KRW' | 'USD'; sourceIds: string[]; locator: string }
  | { status: 'not_disclosed'; sourceIds: string[]; note: string }
  | { status: 'not_applicable'; note: string };
type EarningsRecord = {
  id: string;
  company: CompanyId;
  scope: ScopeId;
  periodLabel: string;
  periodStart: string;
  periodEndInclusive: string;
  periodKind: 'quarter' | 'year_to_date' | 'full_year';
  framework: Framework;
  adjustment: Adjustment;
  metrics: Partial<Record<MetricName, MetricValue>>;
  publishedAt: string;
  reviewedAt: string;
  reviewStatus: 'draft' | 'source_checked' | 'cross_checked';
  supersedesRecordId: string | null;
};
```

금액은 `amount × scale`로 원통화 기준 금액을 얻는다. 예를 들어 원문 USD million 단위 1,000이면 amount='1000', scale='1000000', currency='USD'다. 54.23 billion USD이면 amount='54.23', scale='1000000000'이다. scale은 양의 정수만 허용한다.

DecimalString은 정규식 `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$`로 검사한다. 소수 자릿수를 정수 분자/10의 거듭제곱 분모로 변환하고 scale을 곱해 정확한 유리수 금액을 만든다. 일반 사용자 원화 입력은 정수만 허용하지만 편집자가 넣는 원시 재무 데이터는 검증된 소수 표기를 허용한다. JavaScript 부동소수점으로 먼저 변환하지 않는다.

원문이 소수 조원으로만 공개된 경우 그 정밀도 한계를 기록한다. 원시 재무표의 더 정밀한 수치가 확보되기 전에는 성장률을 과도한 자릿수로 계산하지 않는다.

## 4. 배포 데이터셋 모델

```ts
type EarningsDataset = {
  id: string;
  version: string;
  cutoffDate: string;
  mainRecordIds: {
    samsungConsolidated: string;
    hynixConsolidated: string;
    micronConsolidated: string;
  };
  referenceRecordIds: string[]; // 삼성 DS·마이크론 조정 실적 등
  priorComparisons: {
    currentRecordId: string;
    priorQuarterRecordId?: string;
    priorYearRecordId?: string;
  }[];
  records: EarningsRecord[];
  claims: EditorialClaim[];
  sourceIds: string[];
  fxPolicyId: string | null;
};
```

위 mainRecordIds·referenceRecordIds는 개념 설명이며 실제 코드는 기존 snapshot.recordIds·segmentRecordIds에 매핑한다. 다음 분기로 자동 이동하지 않는다. 업데이트 담당이 기간·출처·요약을 검토하고 새 snapshot을 등록한다. 삼성 DS를 연결실적용 메인 ID에 넣으면 기존 검증과 마찬가지로 실패해야 한다.

기간 형식은 실적 공시의 종료일 포함 표기를 유지한다. 공통 rule의 배타적 유효기간과 혼동하지 않게 `periodEndInclusive`라는 필드명을 사용한다.

## 5. 데이터 입력·검토 워크플로

1. 편집자가 회사 공식 실적 발표와 재무표·공시를 수집한다.
2. 원문 지표명·단위·분기/연간 여부·부문을 장부에 기록한다.
3. 원시 레코드를 draft로 만든다.
4. 각 핵심 값의 원문 위치와 재무표를 대조한다.
5. 반올림·단위·내부거래 조정 때문에 차이가 있으면 note에 근거를 남긴다.
6. 원시 값으로 이익률·변화를 재계산한다.
7. 검토 완료 레코드만 dataset mainRecordIds에서 참조한다.
8. 표·차트·본문 수치 참조와 수정 이력을 함께 빌드한다.

출처는 [기획서 공식 자료 표](../../plan/202611/05_반도체_3사_실적_비교_2026_갱신_기획.md)를 출발점으로 한다. 뉴스룸의 설명을 근거로 기재한 경우에도 수치 출처는 실제 재무표 위치를 보강한다. 이번 설계 문서에는 검토되지 않은 최종 실적 데이터를 채우지 않는다.

## 6. 정규화·파생 지표 함수

```ts
normalizeMetric(metric): NormalizedMetric
calculateOperatingMargin(record): MetricResult<Ratio>
calculateComparableGrowth(current, prior): MetricResult<Ratio>
calculateMarginChange(current, prior): MetricResult<PercentagePoint>
buildComparisonRows(dataset): ValidationResult<ComparisonRow[]>
buildMarginChart(rows): MarginChartModel
validateEarningsDataset(dataset): ValidationReport
```

정규화 금액은 currency를 포함한 정수 또는 정확한 유리수다. KRW와 USD는 단위 없는 숫자로 더하거나 빼지 못하게 금액 타입에 currency를 유지한다.

이익률은 같은 record의 영업이익/매출×100이다. 매출 0·미공개·부재인 경우 `unavailable`이며 0%로 만들지 않는다. 음수 영업이익의 이익률은 유효한 음수 값이다.

성장률은 같은 company·scope·framework·adjustment·currency·periodKind가 일치하고 비교 관계가 명시된 레코드끼리만 계산한다. 분기 일수가 다르면 비교 가능하더라도 차이를 주석으로 설명한다. 양의 비교 기준에만 일반 %를 적용하고 흑자/적자 전환은 별도 상태다.

```ts
type GrowthResult =
  | { kind: 'percentage'; ratio: Ratio }
  | { kind: 'turnaround'; direction: 'to_profit' | 'to_loss'; difference: NormalizedMetric }
  | { kind: 'loss_change'; direction: 'narrowed' | 'widened' | 'unchanged'; difference: NormalizedMetric }
  | { kind: 'not_comparable'; reason: string };
```

원시 값을 먼저 계산하고 금액은 표시 단위, 이익률은 소수 1자리 등 displayPolicy에서 마지막 반올림한다. 원문 공식 비율을 별도 보관한다면 계산 비율과 오차 허용치를 원문 정밀도에 맞춰 비교한다.

## 7. 표 ViewModel

```ts
type ComparisonRow = {
  recordId: string;
  companyLabel: string;
  scopeLabel: string;
  periodLabel: string;
  periodRangeLabel: string;
  frameworkLabel: string;
  revenue: MetricDisplay;
  operatingIncome: MetricDisplay;
  operatingMargin: MetricDisplay;
  yearOverYear: MetricDisplay;
  sourceAnchors: string[];
  comparabilityNotes: string[];
};
```

각 숫자와 기간·범위가 같은 행/카드에 붙어 있어야 한다. 데스크톱 표를 모바일에서 카드로 바꿔도 부문과 회계분기는 생략하지 않는다. 값이 없으면 미공개/해당 없음/계산 불가를 구분한다.

숫자 정렬은 회사의 공시값 비교 기능으로만 제공할 수 있지만 1차 배포에서는 연결실적의 고정 순서 삼성전자→SK하이닉스→마이크론을 유지한다. 삼성 DS는 별도 사업부 표다. 통화가 다른 원통화 매출을 크기 순으로 정렬하는 UI는 제공하지 않는다.

## 8. 차트 설계

필수 이익률 차트는 데이터셋의 main 3행만 사용한다. X축 라벨은 회사·범위·분기, Y축은 %다. 항상 0을 포함하고 음수가 있으면 음수축도 표현한다. 모든 값이 같은 부호여도 막대 길이 비교가 왜곡되지 않도록 임의 잘라낸 축을 쓰지 않는다.

tooltip: 회사/범위, 분기·실제 기간, 이익률, 원통화 매출·영업이익, 회계 기준. 차트 주변에 비교 한계 주석과 동등 표를 제공한다. 색은 기존 사이트 토큰을 사용하되 회사 구분을 색에만 의존하지 않는다.

매출 추이는 회사별 원통화 소형 차트로 제한한다. 공통 지수 차트는 비교 기준 recordId가 명시되고 동일 기준값 100으로 정규화한 별도 데이터 모델이 있을 때만 추가한다.

HBM·DRAM·NAND 구성은 상호 배타적인 공개 범주만 합산한다. DRAM에 포함된 HBM을 별도 더하지 않는다. 세 회사 범주 정의가 다르면 병렬 카드와 주석으로 보여주고 통일된 누적 막대를 만들지 않는다.

## 9. 환율 확장 설계

1차 dataset의 fxPolicyId는 null이다. 원통화 데이터와 이익률만으로 핵심 비교를 제공한다.

추가할 경우:

```ts
type FxPolicy = {
  id: string;
  fromCurrency: 'USD';
  toCurrency: 'KRW';
  method: 'period_average' | 'common_reference_average';
  periodStart: string;
  periodEndInclusive: string;
  rate: SerializedRatio;
  sourceIds: string[];
  rationale: string;
};
```

적용 대상·환율 기간·자료 제공기관을 함께 보인다. 환산값은 ‘비교용 환산’이며 공식 재무제표의 원화 환산 결과라고 하지 않는다. 실제 공시 환산과 환율·범위가 다를 수 있다. 서로 다른 기간의 환율 평균과 공통 기준 환율 중 무엇을 선택했는지는 방법론에 명시한다.

## 10. 해설·전망과 숫자의 연결

```ts
type EditorialClaim = {
  id: string;
  kind: 'reported_fact' | 'management_comment' | 'editorial_analysis';
  textTemplate: string;
  metricRefs: string[];
  sourceIds: string[];
  periodRef: string | null;
};
```

‘매출 ○○조원’ 같은 문장은 `metricRefs`에서 표와 같은 값을 주입한다. 편집 해석은 수치가 바뀌면 그대로 맞는다고 가정하지 않고 재검토 대상으로 표시한다. 텍스트 자동 생성이 곧 분석 검증을 대체하지 않는다.

전망은 actual record와 분리한 GuidanceRecord로 관리한다. 대상 기간·발표일·단위·회사 설명·출처를 갖고 미래 기대값을 실적 차트에 섞지 않는다. 가이던스가 범위면 하한·상한을 그대로 보존한다.

## 11. 검증 사례와 오류

아래 숫자는 실제 기업 실적이 아닌 합성 단위 검증 데이터다.

| ID | 입력 | 기대 |
|---|---|---|
| T5-01 | amount 1000, scale 10^6, USD | 10억 달러, 1 billion USD |
| T5-02 | revenue 1,000, income 250, 같은 통화·scale | 영업이익률 25.0% |
| T5-03 | revenue 1,000, income -100 | -10.0%, 음수축 표시 |
| T5-04 | revenue 0 | 이익률 계산 불가 |
| T5-05 | 이전 매출 800→현재 1000 | +25.0% |
| T5-06 | 이전 이익 -100→현재 50 | 흑자전환, 일반 성장률 미표시 |
| T5-07 | GAAP current / Non-GAAP prior | 비교 기준 불일치로 중단 |
| T5-08 | current quarter / prior full_year | 비교 중단 |
| T5-09 | 삼성 DS ID를 연결실적 main에 삽입 | 데이터셋 검증 실패 |
| T5-10 | 마이크론 fiscal label과 기간 누락 | 공개 데이터셋 빌드 실패 |
| T5-11 | 미공개 HBM 값 | 0% 그래프가 아닌 미공개 |
| T5-12 | 최신 정정 record 참조 | 표·차트·요약이 같은 새 버전 |

오류 코드: ER_SOURCE_MISSING, ER_PERIOD_MISSING, ER_SCOPE_MISMATCH, ER_BASIS_MISMATCH, ER_UNIT_INVALID, ER_RECORD_UNREVIEWED, ER_DUPLICATE_MAIN_RECORD, ER_ZERO_REVENUE, ER_MISSING_METRIC. 핵심 비교표를 만들 수 없는 오류는 배포 검증 실패, 선택 지표 오류는 해당 영역 비활성으로 구분한다.

## 12. 갱신·배포·복구

기존 페이지를 백업하고 새 dataset version을 연결한다. 기존 요약에서 제거·정정한 수치는 변경 이력에 사유를 남긴다. 공시 기준일과 페이지 수정일은 별도 필드다. URL·canonical은 유지한다.

검색 메타·OG에 숫자를 넣을 경우 같은 dataset에서 생성하고 수동 입력을 피한다. 확인 안 된 최신성을 나타내는 ‘방금 발표’ 등 상대 표현은 사용하지 않는다. FAQ·본문·출처의 링크 검수와 기존 성과급 콘텐츠와의 상호 연결을 확인한다.

정정 공시 발견 시: 영향 metricRef 찾기 → record 새 버전 → 파생 지표·표·차트 재생성 → 해설 재검토 → 변경 이력 → 배포. 롤백할 경우 잘못된 수치가 재공개되지 않도록 오류 항목을 숨기거나 정정 안내를 유지한다.
